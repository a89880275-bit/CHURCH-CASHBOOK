## 2. JSON 저장 구조와 안전 경계

```text
.private/accounting/             버전 관리·정적 배포 제외
  current.json                   format + checksum + payload
  snapshots/<revision>-<hash>.json  변경 전 복구 사본
  sessions/<sha256(token)>.json   서버 세션 (토큰 원문 없음)
  write.lock/                    변경 작업 중에만 존재
```

`payload`는 기초정보(users, departments, assignments, accounts), 해당 변경 감사, schemaVersion 및 revision입니다. accounts는 기존 v1 스키마에 선택적 기본 빈 배열로 추가했으며, 기존 계정 없는 자료도 읽을 수 있습니다. 서버 메모리를 원본으로 사용하지 않습니다. 거래는 이번 단계에 포함하지 않았고, 앞으로 거래별 독립 객체 저장 설계를 유지합니다.

저장 순서:

1. 해당 디스크의 `mkdir(write.lock)`으로 협력하는 writer 간 배타 접근. 제한 시간 동안 잠기면 503이며 오래됐다는 이유로 잠금을 강제 탈취하지 않습니다.
2. 최신 JSON 체크섬/스키마 확인 → expectedRevision 비교(불일치 409) → 현재 사용자 활성 상태·역할·부서 권한을 커밋 경계 안에서 재검사.
3. 기초정보와 감사이력 후보를 함께 검증. 변경 전 스냅샷을 독점 생성하고 flush합니다. 백업 사본 생성 실패 시 현재 파일을 바꾸지 않습니다.
4. 같은 디렉터리에 고유 임시 파일 작성·flush → rename으로 현재 파일 교체. Windows의 일시적인 EPERM/EACCES/EBUSY는 잠금을 유지한 채 교체만 최대 1.5초 제한 재시도합니다. 원본을 unlink하거나 직접 truncate해서 쓰지 않습니다. 영구 거부 시 503으로 실패하고 원본을 보존합니다.
5. 임시 파일·잠금을 정리합니다. 변경 실패는 성공 응답으로 표시하지 않습니다. 실패 시 재조회 후 명시적으로 재시도해야 합니다.

검증한 범위는 이 Windows 로컬 디스크에서의 API·파일 오류·프로세스 경합입니다. Node 문서는 flush 구현이 OS/장치에 따라 다름을 명시합니다. 전원 차단·장치 고장·네트워크 드라이브·공유/동기화 폴더·Netlify 분산 실행의 무결성을 보장하지 않습니다. **[Node 파일시스템 공식 문서](https://nodejs.org/api/fs.html)**

같은 서버의 기초정보 변경은 전역 revision을 사용하므로 서로 다른 부서를 수정해도 409가 발생할 수 있습니다. 조용히 덮어쓰는 대신 재조회·재입력을 요구하는 저빈도 기초정보용 구현입니다. 원장/마감 동시성 보장을 이 구조가 이미 충족했다고 판단하지 않습니다.

## 3. 저장소 검증 결과

| 검증 요청 | 결과 | 범위 |
|---|---|---|
| 사용자별 접근권한 | 통과 | 비인증 401, 담당자 관리자 API 403, 중지/역할 변경 기존 세션 적용 |
| 부서별 접근 제한 | 통과 | 범위 밖 계정 읽기·쓰기 403, 다른 부서 계정 ID로 PATCH 차단 |
| JSON 읽기·쓰기 | 통과 | 실제 파일 저장·새 Repository 인스턴스 재조회, 초기화 시 덮어쓰기 금지 |
| 동시 저장 데이터 유실 방지 | 통과 | 독립 Node 프로세스 2개 중 성공 1/409 1, 재조회 후 명시적 재시도로 두 변경 보존 |
| 읽기와 교체 경합 | 통과 | 반복 저장 중 독립 읽기에서 항상 완전한 검증 가능 스냅샷 |
| 쓰기 실패 시 원본·감사 보존 | 통과 | flush 후 publish 직전 오류 주입 및 복구 사본 쓰기 실패 시 기존 JSON 바이트 동일 |
| 잘못된 데이터 차단 | 통과 | 잘못된 참조·중복·마지막 관리자 제거·체크섬 손상 차단, 자동 초기화/초기값 덮어쓰기 없음 |
| 고아 잠금 | 통과 | 강제 탈취 없이 503, 원본 보존 |
| 백업/복원 가능성 | 저장 계층 테스트 통과 | 이전 revision 사본 읽기·체크섬 확인·원상복구 연습. 웹 복원 기능 완료 아님 |
| 정적/개발 경로 비공개 | 통과 | 빌드 산출물 검사, Vite 일반/raw/import/@fs 경로 403 |
| 원격 Blobs 읽기·쓰기·동시성 | 미검증 | 원격 자격증명·운영 사이트 미연결, 업무 쓰기 차단 유지 |

변경 전 사본은 **동일 디스크 복구 사본**입니다. 별도 장애 영역 백업·암호화·보존 주기·자동 백업은 아닙니다. 스냅샷의 체크섬은 손상 탐지용으로, 디스크 파일과 체크섬을 함께 바꿀 수 있는 OS 사용자의 악의적 변조까지 방지하지 않습니다. 로컬 파일 접근권한을 관리하고 신뢰할 수 있는 로컬 디스크에서만 사용해야 합니다.

중단 후 `write.lock`이 남으면 서버를 모두 종료하고 원본/스냅샷을 별도로 보존·검증한 뒤 관리자가 잠금 디렉터리를 확인하여 해제해야 합니다. 손상된 current 파일을 자동으로 과거 사본으로 되돌리지 않으므로, 복구에 따른 데이터 손실 여부를 먼저 확인해야 합니다. 웹 복원 정책은 후속 단계에서 구현합니다.

## 4. API 연결 및 오류 확인

| 경로 | 현재 동작 |
|---|---|
| GET `/api/admin/master` | 관리자 사용자(인증 subject 제외)·부서·배정·revision 조회 |
| GET/POST/PATCH `/api/admin/users` | 조회·등록·이름/역할/상태 변경 |
| GET/POST/PATCH `/api/admin/departments` | 조회·등록·수정·사용 중지 |
| GET/POST `/api/admin/assignments` | 현재/이력 조회·오늘 배정 교체/전체 해제 |
| GET/POST/PATCH `/api/accounts` | 부서 권한 내 조회·등록·수정·사용 중지 |
| GET `/api/admin/audit-logs` | 기초정보 변경 감사 |
| GET `/api/auth/local-identities` | 로컬 진입점에만 존재. 실제 등록된 활성 로컬 검수 계정 목록 |

기존 로그인·logout·me·departments·department-context API는 유지했습니다. 모든 변경 버튼은 위 실제 API에 연결하고, 필수 입력/처리 중 중복 클릭 방지/오류 메시지를 제공합니다. 409 시 최신 revision을 재조회하지만 입력을 자동 저장하거나 다른 사용자의 변경을 덮어쓰지 않습니다.

실행 중인 로컬 URL에서 비인증 `/api/me`는 401, 미설정 `/api/auth/login`은 503, `/.private/accounting/current.json`과 `/server/auth.ts`는 403으로 확인했습니다. 인증 제공자 미설정의 503은 남은 외부 연동 조건이며 일반 로그인 성공처럼 숨기지 않습니다. Vite 개발 파일 차단은 [공식 fs.deny 설정](https://vite.dev/config/server-options.html#server-fs-deny)을 사용하며 별도 테스트에서 확인했습니다.

계정코드는 부서별 유일하고 다른 부서의 동일 코드를 허용합니다. 계정 유형은 거래 참조 인덱스가 아직 없어 이번 단계에서는 등록 이후 전면 변경 금지로 보수적으로 제한합니다. 삭제 API는 만들지 않고 사용 중지로 과거 참조를 보존합니다. 부서 사용 중지를 해제하면 아직 유효한 기존 배정은 다시 적용됩니다.

## 5. 테스트·실행·변경 파일

실행: 터미널 1 `pnpm server`, 터미널 2 `pnpm dev`, 접속 `http://127.0.0.1:5173`. 처음 실행 시 `초기 관리자(owner)` 1명만 생성됩니다. 예제 부서·담당자·계정은 생성하지 않습니다. 이 로그인은 비밀번호 없는 루프백 검수용이며 공개·운영 인증으로 사용하면 안 됩니다. 운영 OIDC·Functions 및 원격 저장소 연결은 별도로 검증해야 합니다.

검증 명령:

```powershell
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vitest/vitest.mjs run
node node_modules/vite/bin/vite.js build
node scripts/check-dist.mjs
```

테스트는 가상값을 OS 임시 디렉터리에 저장하고 종료 시 제거합니다. 사용자용 `.private/accounting`에는 테스트용 부서·계정을 남기지 않습니다.

- 기존 권한·스키마: 38개.
- 실제 로컬 저장소: 15개(실제 두 프로세스 및 Windows 일시/영구 파일 교체 거부 검증 포함).
- 기초정보 파일 저장 API: 20개(인가 재검사·일관된 감사·실패 보존 포함).
- Vite 비공개 경로: 1개.
- 최종: **74/74 통과**, TypeScript·Vite 빌드·dist 검사 통과.
- 재검증 중 읽기/교체 경합 테스트에서 Windows EPERM이 간헐적으로 발생했습니다. 원본을 삭제하지 않는 제한적 rename 재시도와 영구 실패 보존 처리를 추가하고, 해당 실패 모드 테스트 및 전체 테스트를 다시 실행했습니다.
- 브라우저: JSON 초기 관리자 로그인/사용자 조회, 등록 폼·취소, 부서 빈 상태, 390×844 모바일 부서 등록 폼·키보드 Escape 취소, 부서 미선택 계정 화면 확인. 실제 저장 동작은 위 파일 기반 API 통합 테스트에서 확인했습니다.
- 최초 브라우저 기존 탭 제어 연결은 사용할 수 없어 같은 브라우저의 검증용 새 탭에서 확인했습니다. 기존 서버 포트 점유를 확인하고 이 프로젝트의 이전 API만 재시작했습니다.

## 6. 미구현 기능과 다음 단계

1. 다음 **2단계: 장부** — 거래별 JSON 저장, 계정/부서 참조·유형 검사, 기간/검색, 수입·지출 등록·수정·논리삭제, 작성자 불변, 감사, 합계·기초잔액. 거래/마감과 권한의 커밋 경계를 검증한 뒤 연결합니다.
2. **3단계: 통계** — 월별·계정별·연간 합계, 이월/기초잔액, 부서 및 관리자 통합 대시보드. 현재 대시보드의 수치는 여전히 미연결 표시입니다.
3. **4단계: 운영** — 월·연 마감, Excel, 웹 JSON 백업/복원 검증·미리보기·승인·복원 전 백업, 외부 장애 영역 백업, 보존 정책, Netlify 통합검증·배포.
4. **외부 연동** — 실제 OIDC 업체/계정·초기 관리자 매핑, 원격 JSON 저장소의 실제 조건부 갱신·실패·경합 검증. 운영 Blobs 차단을 단순 환경변수로 해제하는 기능은 추가하지 않았습니다.

이번 단계는 **로컬 비공개 JSON을 기준으로 1단계 기초정보를 동작하게 만든 결과**입니다. 전체 회계 시스템이나 Netlify 운영 준비의 완료로 해석하지 않습니다.
