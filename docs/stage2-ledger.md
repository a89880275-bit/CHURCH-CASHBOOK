# 2단계 — 수입·지출 장부 구현 결과

기준 문서: `accounting_web_codex_spec.md` v1.0. 확인일: 2026-11-06. 기존 구조·로그인·부서 권한·다크 UI를 유지하고 `/ledger` 안내 화면을 실제 업무 화면으로 교체했습니다.

## 1. 구현 완료 범위

| 진행 순서 | 구현 결과 |
|---|---|
| 거래 저장소 | 부서/거래/버전별 독립 JSON 객체, 체크섬 검증, 현재 유효 거래 참조와 감사이력의 동시 확정 |
| 거래 API | 수입·지출 등록/수정/논리삭제, 현재 권한·부서 활성 상태·계정 소속/유형/활성 상태 검사 |
| 장부 화면 | 부서 선택, 수입/지출 등록창, 수정·삭제 확인 및 사유, 이력 전후 비교 |
| 목록·검색 | 시작/종료일·유형·계정·적요/비고 검색, 정렬·25/50/100건 페이지·삭제 이력 포함 |
| 합계·잔액 | 조회 결과 전체 수입·지출·차액, 관리자의 기초잔액 설정/수정, 기간말 누적잔액 |
| 검증 | 다른 부서 차단, 인수인계 후 자료 보존, 두 프로세스의 독립 거래 저장, 같은 거래 수정 충돌, 저장 실패 보존 |

전체 부서 선택 상태에서는 특정 부서를 선택하라는 업무 안내를 표시하고 거래 입력을 차단합니다. 부서가 아직 없으면 부서관리 → 부서 등록 → 계정코드 등록을 먼저 진행하세요. 등록된 사용자 자료 대신 예제 부서/거래를 생성하지 않습니다.

## 2. 저장 방식과 동시성

```text
.private/accounting/
  current.json                      제어 정보·현재 거래 참조·감사·기초잔액·마감 상태
  transactions/{departmentId}/{transactionId}/{version}-{hash}.json
                                    변경하지 않는 거래 버전 객체
  snapshots/{revision}-{hash}.json   이전 제어 스냅샷
  sessions/                         서버 세션
  write.lock/                       로컬 커밋 잠금
```

거래 객체를 먼저 저장·flush·재검증한 다음, 기초정보 변경과 **동일한 디스크 잠금** 안에서 최신 사용자/배정·계정·마감 상태를 다시 읽습니다. 후보 거래 참조·감사·합계를 검증하고 제어 스냅샷을 교체한 경우에만 커밋된 거래로 취급합니다. 디렉터리의 파일 목록으로 거래 목록을 만들지 않습니다.

- 서로 다른 거래: 잠금 안에서 최신 참조 목록에 추가하여 둘 다 보존합니다. 거래 생성에 전역 expectedRevision을 요구하지 않습니다.
- 같은 거래 수정/삭제: `expectedVersion`과 현재 거래 참조의 version 비교. 한 요청만 성공하고 다른 요청은 409이며 무조건 덮어쓰지 않습니다.
- 등록 재시도: 클라이언트가 생성한 UUID `requestId`를 사용합니다. 이미 저장된 동일 작성자·동일 내용의 요청은 기존 거래를 반환해 중복 등록을 막습니다. 같은 ID의 다른 내용은 409입니다. 이 ID를 사용자나 부서 권한의 증거로 신뢰하지 않습니다.
- 객체 쓰기/제어 스냅샷 교체 실패: 기존 참조·원본 거래·감사이력을 변경하지 않습니다. 아직 참조되지 않은 객체가 디스크에 남을 수 있으나 목록/합계에는 포함하지 않습니다.
- 거래 수정: 기존 버전 객체를 덮어쓰지 않고 새 버전을 추가합니다. departmentId, createdBy, createdAt은 유지하고 updatedBy/updatedAt/version을 갱신합니다.
- 논리삭제: 새 버전에 status=DELETED 및 deletedBy/deletedAt/deletionReason을 기록합니다. 원본과 감사는 남기고 활성 합계에서 제외합니다.
- 마감 검사: 현재 제어 스키마의 CLOSED 월에는 관리자도 거래 생성/수정/삭제 불가. 날짜 이동 시 기존 월과 이동 월을 모두 검사합니다. 마감 상태가 객체 저장 중 변경돼도 커밋 직전에 다시 검사합니다. **마감 실행·해제 UI/API 자체는 다음 운영 단계입니다.**

이 구현은 **현재 Windows 로컬 디스크**를 대상으로 검증했습니다. Netlify의 임시 디스크를 영구 저장소로 사용하지 않으며, Netlify Blobs의 분산 원자성을 검증했다고 설명하지 않습니다. 지원하지 않는 저장 어댑터의 장부 읽기/쓰기는 503으로 차단합니다. 기존 운영 Blobs 업무 쓰기 차단도 그대로입니다.

전원 차단·디스크 장애·공유/동기화 드라이브·고빈도 대용량 쓰기 보장은 없습니다. 잠금은 만료됐다는 이유로 강제 탈취하지 않습니다. 이전 단계의 Windows rename 제한 재시도를 유지합니다. 부서 참조 건수는 20,000건을 상한으로 제한하며, 이 규모 전체의 성능 부하 시험을 통과했다는 뜻은 아닙니다. 현재 커밋은 부서 전체 거래 검증을 수행하므로 큰 원장의 잠금 대기·지연은 별도 확장 설계가 필요합니다.

## 3. 계산·기초잔액 정책

- 금액은 원 단위 양수 safe integer입니다. 합계는 BigInt로 계산하고 안전한 정수 범위를 넘으면 저장/응답을 거부합니다. 반올림하거나 초과 값을 자르지 않습니다.
- 조회 수입/지출/차액은 **모든 페이지의 검색 결과 중 활성 거래** 합계입니다. 삭제 이력을 표시해도 삭제 금액은 합계에 더하지 않습니다.
- 기초잔액이 없으면 누적잔액을 null/`—`로 표시합니다. 미설정을 임의의 0원으로 바꾸지 않습니다.
- 관리자만 적용일·금액·사유를 명시해 기초잔액을 설정/수정합니다. 명시적 0원, 음수 잔액도 허용합니다. 최초 작성자·시각과 변경 감사는 보존합니다.
- 기초잔액은 적용일 시작 전 잔액입니다. 적용일부터 조회 종료일까지의 **모든 활성 거래**를 한 번씩 반영합니다. 시작일·적요·유형·계정 검색과 기간말 잔액을 구분합니다. 화면에 “검색필터 제외”를 표시합니다.
- 기존 활성 거래보다 늦은 날짜로 기초잔액을 적용하지 못합니다. 적용일 이전 거래 등록도 거부합니다. 종료일이 기초잔액 적용일 이전이면 해당 기간 잔액은 미확정으로 표시합니다.
- 마감된 기간에 영향을 미치는 기초잔액 변경은 거부합니다. 자동 이월 거래를 중복 생성하지 않습니다. 연간 결산·연도별 기초/이월 관리 표는 다음 통계 단계입니다.

## 4. API

| 메서드·경로 | 기능 |
|---|---|
| GET `/api/transactions` | 부서 장부·검색·페이지·합계·기간말 잔액·계정·마감 월 조회 |
| POST `/api/transactions` | requestId로 새 거래 등록 |
| PATCH `/api/transactions` | id/departmentId/expectedVersion과 수정 사유로 변경 |
| DELETE `/api/transactions` | id/departmentId/expectedVersion과 삭제 사유로 논리삭제 |
| GET `/api/transactions/detail` | 권한 범위 내 거래 한 건. 충돌 후 명시적 최신 값 불러오기 |
| GET `/api/transactions/history` | 해당 부서 거래의 등록/수정/삭제 감사 및 변경 전후 |
| POST `/api/admin/opening-balances` | 관리자 기초잔액 설정/수정, expectedRevision 및 사유 필수 |

목록 쿼리: departmentId 필수, from/to, type(INCOME/EXPENSE), accountId, keyword, page/pageSize, sort(date_desc/date_asc), includeDeleted(0/1).

모든 API에서 로그인 사용자와 현재 권한을 재검사합니다. 등록/수정 본문의 createdBy·createdAt·status 등 서버 필드 주입은 엄격한 스키마로 거부합니다. 표준 오류: 미인증 401, 부서 권한 없음 403, 범위 내 거래 미존재 404, 버전/마감 충돌 409, 입력/합계 오류 422, 저장 실패·무결성 오류·미지원 어댑터 503. 변경 요청의 Origin 및 JSON 검사를 유지합니다.

충돌 시 편집창은 초안을 유지합니다. “입력 버리고 최신 거래 불러오기”를 선택하면 최신 거래를 읽어 다시 편집합니다. 클라이언트가 버전을 자동 증가시켜 기존 내용을 덮어쓰지 않습니다.

## 5. 실행·테스트 결과

실행 방법은 동일합니다. 기존 API를 종료 후 `pnpm server`, 다른 터미널에서 `pnpm dev` 실행 → `http://127.0.0.1:5173/ledger` 접속. 현재 실행 중인 API도 새 코드로 재시작했습니다.

```powershell
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vitest/vitest.mjs run
node node_modules/vite/bin/vite.js build
node scripts/check-dist.mjs
```

검증 결과: **106/106 테스트 통과**, TypeScript 검사·Vite 빌드·정적 산출물 검사 통과.

- 기존 74개 회귀 테스트 유지.
- 장부 32개: 파일 영구 저장·읽기, 부서/계정 참조·유형·활성 검사, 작성자 위조 차단, 수정/삭제 이력, 검색·페이지·합계, 기초잔액 미설정/0원/기간말 계산, 같은 거래 수정 충돌, 서로 다른 거래의 실제 독립 Node 프로세스 저장, 인수인계 후 기존 세션 회수·후임 열람·다른 부서 유지, 마감/권한/계정 변경 경합, 객체/제어 저장 실패, 변조 차단, 합계 오버플로, 기존 JSON의 신규 필드 기본값 호환, 미지원 저장소 차단.
- 기존 검증 중 EPERM 문제를 수정한 파일 교체 처리를 유지했습니다. 장부 테스트에서 새로운 실패는 발견되지 않았습니다.

브라우저 검증은 사용자용 JSON과 다른 **OS 임시 디렉터리 + localhost:5174/별도 API 포트**에서 수행했습니다. 쿠키도 사용자용 127.0.0.1 호스트와 분리했습니다.

1. 검증용 교육부 선택 → 기존 수입 120,000원/지출 35,000원 조회, 잔액 미설정 표시 확인.
2. 수입 등록 25,000원 → 합계 145,000원.
3. 해당 거래 30,000원으로 수정 → 수입 합계 150,000원, 이력에 25,000 → 30,000원.
4. 사유 입력 후 논리삭제 → 수입 합계 120,000원 복귀. 삭제 이력 포함 → 등록/수정/삭제 세 이력 확인.
5. 검증 기초잔액 1,000,000원 설정 → 기간말 1,085,000원 확인.
6. “교재” 검색 → 조회 차액 -35,000원, 기간말 잔액은 1,085,000원 유지.
7. 390×844 모바일에서 필터·2열 합계·지출 등록 폼·계정 유형 필터·스크롤·Escape 취소 확인.

증빙 `docs/screenshots/stage2-ledger-qa.png`는 **격리된 검증용 JSON** 화면입니다. 실제 교회 잔액을 보여주는 이미지가 아닙니다. 검증 서버와 사용한 임시 자료는 정상 종료 시 정리했습니다. 사용자 `.private/accounting`에는 검증용 거래·기초잔액을 추가하지 않았습니다.

선택적으로 같은 수동 검증 환경을 재현하려면 `node --import tsx tests/fixtures/ledger-preview.ts`를 대화형 터미널에서 실행하고 `http://localhost:5174/ledger`에 접속하세요. 끝나면 해당 터미널에 `exit`를 입력해 종료·정리합니다. 운영 데이터 이관이나 데모 데이터 설치 도구가 아닙니다.

## 7. 미구현 및 다음 단계

- 다음 **3단계 통계·대시보드**: 실제 원장 기반 월별/계정별/연간 합계·표·차트, 부서 대시보드 및 관리자 전체 부서 통합. 현재 `/` 대시보드는 아직 회계 수치 미연결 상태입니다.
- 운영 단계: 월·연 마감 실행/해제 화면·API, Excel, 웹 백업/복원 미리보기·승인·무결성 검증, 외부 장애 영역 백업·보존 정책.
- 원격 운영: 관리형 OIDC 실제 연결, Netlify 원격 JSON 저장의 경합·실패·배포 지속성 검증, 실제 배포. 이 단계 결과를 Netlify 운영 완료로 취급하지 않습니다.
- 백업 시 제어 JSON만으로 거래를 복원할 수 없습니다. 해당 스냅샷이 참조하는 거래 객체/이력도 함께 필요합니다. 참조되지 않은 객체/이전 버전의 자동 정리는 아직 없으며 복구 가능성을 검토하기 전 삭제하지 않습니다.
