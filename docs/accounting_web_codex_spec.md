# 부서별 웹 수입·지출 회계관리 시스템

> Codex 개발용 통합 요구사항 및 화면설계서  
> 버전: 1.0 / 작성일: 2026-11-06  
> 배포: Netlify / 데이터: 비공개 JSON 객체 저장 / 계정: 다중 사용자

## 1. 프로젝트 개요

### 1.1 배경
기존 Delphi 기반 수입·지출 장부는 특정 PC에서만 이용할 수 있다. 웹 브라우저에서 접속할 수 있도록 전환하고, 여러 회계담당자가 각자 배정받은 1~3개 부서의 회계를 독립적으로 운영한다.

### 1.2 확정 정책
1. 시스템 관리자는 전체 사용자, 부서, 담당자 배정, 회계자료, 통계 및 백업을 관리한다.
2. 일반 회계담당자는 자신에게 **현재 배정된 부서**의 자료만 조회·입력·수정할 수 있다.
3. 모든 회계자료는 사용자 개인이 아니라 **부서 ID**에 귀속된다. 담당자가 교체되어도 과거 거래, 계정코드, 잔액, 마감 및 감사기록은 유지된다.
4. 계정코드는 **부서별 독립 관리**한다. 다른 부서에 같은 코드가 있어도 별개로 취급한다.
5. Netlify에 웹을 배포하며, 별도 DB 서버 설치 없이 비공개 JSON 객체 저장소를 사용한다.
6. PC 우선 반응형 모던 다크 UI를 사용한다.
7. 관리자가 담당자 교체 시 기존 담당자 권한을 회수하고 새 담당자에게 기존 자료의 열람 권한을 부여한다.

### 1.3 범위
- 포함: 로그인, 사용자/부서/권한 관리, 부서별 계정코드, 수입·지출 장부, 대시보드, 월별/계정별 집계, 마감, 감사이력, JSON 백업·복원, Excel 내보내기.
- 초기 범위 제외: 은행 자동연동, 전자결재, 세금신고, 복식부기, 모바일 앱 설치, 외부 회계 시스템 연계.

## 2. 기술 아키텍처

### 2.1 권장 스택
- Frontend: React + TypeScript + Vite
- UI: Tailwind CSS, Lucide 아이콘, 접근성 있는 컴포넌트
- Charts: Recharts
- Hosting: Netlify
- API: Netlify Functions (서버 측 인증·권한 검사·데이터 접근)
- Storage: Netlify Blobs 등 **비공개 JSON 객체 저장소**
- Export: ExcelJS 또는 SheetJS
- Validation: Zod 등 스키마 검증
- Testing: Vitest, React Testing Library, Playwright

### 2.2 필수 아키텍처 원칙
브라우저 → HTTPS → Netlify Functions → 인증/인가 검사 → 비공개 JSON 저장소.

**금지 사항:** `public/` 또는 배포 산출물에 사용자/비밀번호/회계 JSON을 넣지 않는다. 브라우저에서 비공개 저장소 키를 사용하지 않는다. 클라이언트가 전달한 `departmentId`, `role`, `userId`를 신뢰하지 않는다. 정적 배포 파일을 수정해 영구 저장하려 하지 않는다.

**중요:** JSON 저장소는 데이터베이스가 아니다. 여러 사용자가 같은 JSON 파일 전체를 읽고 덮어쓰면 업데이트가 유실될 수 있다. Netlify Blobs의 실제 일관성·조건부 갱신 지원 및 배포 간 지속성은 구현 전에 최신 공식 문서와 테스트로 확인한다. 저장소가 제공하지 않는 원자적 다중 객체 트랜잭션, compare-and-swap, 잠금 기능을 있다고 가정하지 않는다.

### 2.3 권장 저장 전략
- 거래는 `transactions/{departmentId}/{transactionId}.json`과 같이 **거래별 독립 객체**로 보관한다. 모든 부서의 거래를 단일 `transactions.json` 파일로 덮어쓰지 않는다.
- 계정코드, 사용자-부서 권한 등 소규모 데이터는 논리적 JSON 컬렉션으로 모델링하되 동시 갱신 충돌을 방지할 수 있는 저장 방식을 선택한다.
- 집계는 거래 원본을 기준으로 계산한다. 캐시가 있다면 무효화·재생성 가능해야 한다.
- **강한 원자성/고빈도 동시 쓰기가 필요한 경우** JSON 객체 저장만으로는 충분하지 않을 수 있다. 해당 경우 SQLite/관리형 DB 전환을 별도 승인 사항으로 제시한다. 회계 데이터의 무결성을 기능 편의보다 우선한다.
- 거래 수정은 버전 검사와 감사 이력을 사용하고, 동시 수정 충돌 시 사용자에게 재조회·재시도를 안내한다. 버전 검사가 저장소에서 원자적으로 보장되지 않는다면 별도 직렬화 수단을 도입하거나 해당 기능을 제한한다.

## 3. 사용자 역할과 접근권한

| 기능 | 관리자 | 회계담당자 |
|---|---|---|
| 로그인/내 정보/비밀번호 변경 | O | O |
| 사용자 생성·중지·권한 초기화 | O | X |
| 부서 생성·수정·비활성화 | O | X |
| 담당자 배정·해제·교체 | O | X |
| 부서별 계정코드 | 전체 | 배정 부서만 |
| 수입·지출 조회/입력/수정 | 전체 | 배정 부서만 |
| 월별/계정별 통계 | 전체 | 배정 부서만 |
| 마감 실행·해제 | O | 조회만 (기본 정책) |
| 감사이력 조회 | 전체 | 본인 담당 부서 내 허용 범위 |
| 전체 백업·복원 | O | X |
| 담당 부서 Excel/JSON 내보내기 | O | O |

- 사용자 상태: `ACTIVE`, `DISABLED`.
- 부서 상태: `ACTIVE`, `INACTIVE`.
- 역할: `ADMIN`, `ACCOUNTANT`.
- 담당자는 복수 부서 배정 가능.
- API 모든 요청에서 서버 측으로 로그인 사용자와 현재 부서 배정을 재검증한다.
- 담당자 변경 후 이전 담당자의 기존 세션도 해당 부서 접근을 즉시 잃어야 한다.
- 관리자라도 삭제·복원·마감 해제 등 위험 작업은 재확인 및 감사기록이 필요하다.

## 4. 담당자 인수인계 시나리오

예: `DEPT001` 교육부, 기존 `USER001`, 신규 `USER007`.

1. 관리자가 [부서관리 > 담당자 배정]에서 교육부를 선택한다.
2. 새 담당자 `USER007`을 지정하고 변경 적용일·사유를 입력한다.
3. 기존 담당자 `USER001`의 교육부 배정을 종료한다. (다른 담당 부서 권한은 유지)
4. 새 담당자에게 교육부의 모든 과거 회계자료 조회 권한과 현재 미마감 기간 입력 권한을 부여한다.
5. 거래의 `departmentId`와 기존 `createdBy`/`updatedBy`는 변경하지 않는다.
6. 배정 변경 이력을 남긴다. 마감된 자료는 담당자 변경으로 수정 가능 상태가 되지 않는다.

**인수인계의 핵심 불변식:** 거래 소유자는 부서이며, 담당자 변경은 거래 데이터를 이전·복제·삭제하지 않는다.

## 5. 데이터 모델(JSON 논리 스키마)

모든 ID는 변경 불가능한 UUID/ULID 등으로 생성한다. 시간은 UTC ISO-8601로 저장하고 UI에서는 한국 시간으로 표시한다. 회계 날짜는 `YYYY-MM-DD`로 별도 저장한다. 금액은 원화 정수로 저장한다(소수점 금지, 0원 입력 정책은 기본 불허).

### 5.1 users
```json
{
  "id": "USER001",
  "loginId": "account01",
  "displayName": "김담당",
  "role": "ACCOUNTANT",
  "status": "ACTIVE",
  "createdAt": "2026-11-06T00:00:00Z"
}
```
인증 비밀값은 별도 인증 제공자 또는 서버 전용 안전한 인증 저장소에서 관리한다. **평문 비밀번호, 재사용 가능한 세션 토큰, 비밀번호 해시를 공개 JSON으로 배포하지 않는다.** 사용자 ID/역할과 인증 주체 매핑은 서버에서 검증한다.

### 5.2 departments
```json
{
  "id": "DEPT001",
  "code": "EDU",
  "name": "교육부",
  "status": "ACTIVE",
  "createdAt": "2026-11-06T00:00:00Z"
}
```

### 5.3 user-departments (배정 이력)
```json
{
  "id": "ASSIGN001",
  "userId": "USER001",
  "departmentId": "DEPT001",
  "validFrom": "2026-01-01",
  "validTo": "2026-12-31",
  "assignedBy": "ADMIN001",
  "reason": "담당자 교체"
}
```
현재 권한은 활성 상태와 적용기간으로 판단하며, 배정 변경 작업은 원자성 확보 또는 실패 복구 전략을 갖춘다. 종료일을 `null`로 둘 수 있다.

### 5.4 accounts (부서별 독립 계정)
```json
{
  "id": "ACC001",
  "departmentId": "DEPT001",
  "code": "I001",
  "name": "회비 수입",
  "type": "INCOME",
  "sortOrder": 10,
  "status": "ACTIVE"
}
```
- 유일성: `(departmentId, code)`.
- 유형: `INCOME` 또는 `EXPENSE`.
- 사용 이력이 있는 계정은 물리 삭제 금지, 비활성화 처리.
- 다른 부서의 계정 ID를 거래에 연결하지 못하도록 서버 검증.

### 5.5 transactions
```json
{
  "id": "TX000001",
  "departmentId": "DEPT001",
  "date": "2026-11-06",
  "accountId": "ACC001",
  "type": "INCOME",
  "description": "11월 회비 수입",
  "amount": 100000,
  "remark": "",
  "createdBy": "USER001",
  "createdAt": "2026-11-06T00:00:00Z",
  "updatedBy": "USER001",
  "updatedAt": "2026-11-06T00:00:00Z",
  "version": 1,
  "status": "ACTIVE"
}
```
- `type`은 계정의 유형과 일치해야 한다.
- 삭제는 기본적으로 논리 삭제하고 삭제 사유·시각·담당자를 기록한다.
- 수정·삭제는 마감 상태와 서버 권한을 확인한다.
- 입력 항목: 거래일, 수입/지출, 계정, 적요, 금액, 비고.
- `createdBy`는 수정해도 바뀌지 않는다.

### 5.6 closings
```json
{
  "id": "CLOSE-DEPT001-2026-10",
  "departmentId": "DEPT001",
  "period": "2026-10",
  "status": "CLOSED",
  "closedBy": "ADMIN001",
  "closedAt": "2026-11-06T00:00:00Z"
}
```
월별 마감이 기본이며 연간 마감은 12개월 확정 여부 확인 후 처리한다. 마감 시점의 집계와 원장 무결성을 검증한다. 마감 해제는 관리자만 사유를 입력하고 감사기록을 남긴다.

### 5.7 audit-logs
`id, actorUserId, departmentId, entityType, entityId, action, before, after, occurredAt, reason`.
- 사용자/권한 변경, 거래 등록·수정·삭제, 마감·해제, 복원 수행을 기록한다.
- 민감한 인증정보는 감사기록에 남기지 않는다.
- 감사기록은 일반 사용자 수정·삭제 불가, 가능한 한 추가 전용으로 보관한다.

## 6. 회계 계산 규칙

- 월 수입 합계 = 해당 부서·월의 활성 `INCOME` 거래 금액 합계.
- 월 지출 합계 = 해당 부서·월의 활성 `EXPENSE` 거래 금액 합계.
- 월 차액 = 월 수입 - 월 지출.
- 기초잔액은 별도 `opening-balances` 레코드 또는 최초 도입 시점의 검증된 이월 금액으로 관리한다.
- 기말잔액 = 기초잔액 + 해당 기간 누적 수입 - 누적 지출.
- 월별 이월잔액 = 직전 월 기말잔액. 중복 이월계상 금지.
- 집계 기준은 거래일(`date`), 금액은 원 단위 정수.
- 조회 필터: 연도, 월 범위, 부서, 계정, 유형, 적요 검색.
- 관리자 전체 부서 통계는 부서별 합계를 집계한 값이며, 동일 거래를 중복 집계하지 않는다.
- 마감 전 거래 변경 시 관련 기간의 통계를 재계산한다.

## 8. 화면 상세 설계

### SCR-01 로그인
- 좌측 브랜드 영역, 우측 로그인 카드(모바일은 단일 열).
- 입력: 아이디, 비밀번호. 비밀번호 표시 토글, 로그인 버튼.
- 실패 시 계정 존재 여부를 노출하지 않는 일반 오류 메시지.
- 계정 비활성화/세션 만료 처리.
- 로그인 후 서버에서 허용 부서를 조회하고, 1개면 자동 선택, 복수면 최근 선택 부서 우선 표시.

### SCR-02 메인 레이아웃
- 좌측 사이드바, 상단 헤더(현재 부서, 회계연도, 사용자, 로그아웃), 본문.
- 부서 드롭다운은 **현재 사용자가 접근 가능한 부서만** 표시.
- 관리자는 '전체 부서' 선택 가능. 전체 선택 상태에서는 거래 입력 불가(특정 부서 선택 유도).
- 권한 없는 메뉴 숨김 + 서버 API에서도 반드시 차단.

### SCR-03 대시보드
- KPI 카드: 이번 달 수입, 이번 달 지출, 월 차액, 현재 누적잔액.
- 월별 수입/지출 막대 차트, 최근 거래 10건, 계정별 지출 상위 항목.
- 연도·부서 선택에 따라 모든 수치 동시 갱신.
- 빈 데이터 상태, 로딩/오류 상태 제공.

### SCR-04 수입·지출 장부
- 상단: 부서, 기간, 유형, 계정, 키워드, 검색/초기화/Excel.
- 목록: 날짜, 유형, 계정코드/명, 적요, 수입금액, 지출금액, 잔액(선택), 작성자, 수정일, 작업.
- 거래 등록: 날짜, 유형, 계정, 적요, 금액, 비고. 계정은 현재 부서/유형에 속한 활성 계정만 표시.
- 수정/삭제: 확인 모달, 마감기간 잠금, 감사이력.
- 정렬·페이지네이션, 목록 합계, 키보드 입력 편의.

### SCR-05 계정코드 관리
- 부서 선택(권한 내), 수입/지출 탭, 코드/명칭/사용여부/정렬순서.
- 추가·수정·비활성화. `(departmentId, code)` 중복 방지.
- 사용 중인 계정의 유형 변경 금지. 비활성 계정은 과거 거래 조회에서 유지.

### SCR-06 월별 수입·지출 통계
- 선택 연도 1~12월 표: 월, 수입, 지출, 차액, 누적잔액.
- 차트/표 전환, 합계 행, Excel 내보내기.
- 월 클릭 시 해당 월 거래 상세로 이동.

### SCR-07 계정별 월별 집계
- 부서·연도·수입/지출 필터.
- 행=계정코드/계정명, 열=1~12월 및 연간합계.
- 계정 클릭 시 거래 목록 드릴다운.
- 가로 스크롤, 첫 열 고정, Excel 내보내기.

### SCR-08 연간 결산
- 연도별 기초잔액, 연간 수입, 연간 지출, 기말잔액.
- 전년도 이월 확인, 월별 마감 현황, 누락된 기초잔액 경고.
- 관리자 승인 후 마감, 일반 담당자 조회.

### SCR-09 사용자 관리 (관리자)
- 사용자 목록: 아이디, 이름, 역할, 상태, 담당 부서, 마지막 로그인(제공 가능 시).
- 사용자 등록·비활성화·권한 변경·비밀번호 초기화 흐름.
- 관리자가 자기 자신의 마지막 관리자 권한을 제거하지 못하도록 방지.

### SCR-10 부서 및 담당자 배정 (관리자)
- 부서 목록과 상세 탭(기본정보, 현재 담당자, 배정 이력).
- 담당자 복수 배정·해제, 변경 적용일/사유 입력.
- 담당자 교체 전후 권한 미리보기 및 확인.
- 이전 담당자의 다른 부서 권한은 유지.
- 부서 비활성화 시 과거 자료는 보존.

### SCR-11 마감 관리 (관리자)
- 부서별 월 마감 상태 달력/테이블.
- 마감 실행 시 거래 검증, 마감 후 입력·수정·삭제 차단.
- 마감 해제 시 사유 필수, 이력 남김.

### SCR-12 감사이력 (관리자)
- 사용자, 부서, 기간, 대상, 작업별 검색.
- 변경 전/후 값 비교, 담당자 변경 이력, 복원 이력.

### SCR-13 백업·복원 (관리자)
- 전체 또는 부서별 JSON 내보내기.
- 백업 파일에 `schemaVersion`, `exportedAt`, 범위, 레코드 수, 체크섬/무결성 정보를 포함.
- 복원은 관리자 재확인 → 파일 검사 → 미리보기 → 기존 데이터 별도 백업 → 복원 → 검증 순서.
- 스키마 불일치, 중복 ID, 잘못된 부서/계정 참조, 권한 없는 복원 차단.
- 자동 백업은 실제 스케줄 실행 수단 및 보존 정책을 확정한 뒤 구현. 단순 다운로드 버튼만으로 자동 백업이라고 표시하지 않는다.

## 10. API 계약 초안

모든 API는 HTTPS, 인증 필수(로그인 제외), 서버 권한 검증, 입력 스키마 검증, 표준 오류 응답을 사용한다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/auth/login` | 인증 제공자 방식에 따라 구현 |
| POST | `/api/auth/logout` | 세션 종료 |
| GET | `/api/me` | 내 정보·허용 부서 |
| GET | `/api/departments` | 허용 부서 목록 |
| POST/PATCH | `/api/admin/departments` | 부서 관리 |
| GET/POST/PATCH | `/api/admin/users` | 사용자 관리 |
| POST | `/api/admin/assignments` | 담당자 배정·교체 |
| GET/POST/PATCH | `/api/accounts` | 부서별 계정코드 |
| GET/POST/PATCH/DELETE | `/api/transactions` | 장부 거래 |
| GET | `/api/reports/monthly` | 월별 수입·지출 |
| GET | `/api/reports/account-monthly` | 계정별 월별 집계 |
| GET | `/api/reports/annual` | 연간 결산 |
| POST | `/api/admin/closings` | 마감/해제 |
| GET | `/api/admin/audit-logs` | 감사이력 |
| POST | `/api/admin/backups/export` | 백업 생성 |
| POST | `/api/admin/backups/restore` | 검증·승인 후 복원 |

응답 예:
```json
{
  "success": false,
  "error": {
    "code": "DEPARTMENT_ACCESS_DENIED",
    "message": "해당 부서에 접근할 권한이 없습니다."
  }
}
```

서버에서 현재 세션의 사용자 식별 → 역할 조회 → 부서 권한 확인 → 요청 처리 순으로 실행한다. 인증된 사용자 ID는 요청 본문이 아닌 서버 검증된 세션에서 가져온다.

## 11. 보안 요구사항

1. 인증은 관리형 인증 제공자 또는 충분히 검증된 서버 측 인증 솔루션을 사용한다. 자체 구현 시 비밀번호는 Argon2id 등 적절한 해시로 보관하고, 비밀번호 초기화·세션 폐기·로그인 시도 제한을 구현한다.
2. 세션 쿠키는 `HttpOnly`, `Secure`, 적절한 `SameSite`를 적용하고 CSRF 위험을 평가한다.
3. 사용자/부서/거래 API 모두 서버 측 인가 확인. 부서 ID를 바꾼 요청도 거부한다.
4. 배포 번들·소스맵·환경변수 노출 점검. 비밀키는 서버 환경변수에만 둔다.
5. 로그에는 비밀번호·세션 토큰·민감정보를 남기지 않는다.
6. XSS/CSRF 방어, 입력 검증, 오류 메시지 정보 노출 최소화.
7. 권한 변경·계정 비활성화 시 기존 세션의 접근권한 재평가.
8. 백업 파일은 민감정보로 취급하고 다운로드 권한·보관 기간·암호화 필요성을 검토한다.
9. 개인정보 최소 수집(로그인 ID, 표시 이름 등) 및 관리자 접근기록 관리.

## 12. 백업 및 운영

- 기본: 관리자의 수동 전체 JSON 백업 및 부서별 내보내기.
- 권장: 별도 저장 위치로 주기적 스냅샷/백업, 일정 기간 보존, 복원 리허설.
- 백업은 원본 저장소와 장애 영역이 분리된 곳에도 보관한다.
- 데이터 정합성 점검: 부서·계정 참조, 거래 금액, 월별 합계, 마감기간 수정 여부.
- 배포: GitHub → Netlify 연동 또는 Netlify CLI 배포. 환경변수는 Netlify 사이트 설정에서 관리.
- 운영: 장애/권한 오류/저장 실패 로깅, 복구 절차 문서화.

### Phase 1 — 기반

## 14. 검수 시나리오(필수)

1. 관리자 A는 모든 부서를 조회한다.
2. 담당자 B에게 교육부·찬양부를 배정하면 두 부서만 보인다.
3. 담당자 B가 API URL의 부서 ID를 선교부로 바꿔도 `403`이다.
4. 교육부 담당자를 B→C로 변경하면 C는 과거 교육부 거래를 조회하고 B는 교육부 접근이 거부된다.
5. B가 기존에 맡은 찬양부 접근권한은 유지된다.
6. 담당자 변경 후 기존 거래의 작성자·변경 이력은 그대로다.
7. 동일 계정코드 `I001`을 교육부·선교부에 각각 등록할 수 있다.
8. 교육부 거래에 선교부 계정 ID를 지정하면 거부된다.
9. 마감된 월의 거래 등록·수정·삭제는 일반 담당자 및 관리자 일반 거래 API에서 거부된다. 해제 절차를 통해서만 가능하다.
10. 두 사용자가 서로 다른 거래를 거의 동시에 저장해도 둘 다 남는다.
11. 동일 거래를 동시에 수정할 때 무조건 마지막 저장으로 덮어쓰지 않는다.
12. 거래 합계, 월별 통계, 계정별 통계, 연간 합계가 일치한다.
13. 백업→복원 후 거래 건수·금액·계정·담당자 이력이 검증된다.
14. 로그인하지 않은 상태에서 API 호출 시 `401`, 권한이 없는 경우 `403`.
15. 정적 배포 폴더에서 회계 JSON, 비밀번호, 서버 비밀키를 찾을 수 없다.
16. 모바일 화면에서 목록·입력·부서선택이 동작한다.

## 16. 후속 확인 사항
