# 교회 공통 계정과목 마스터 설계안 — 승인 전

요청에 따라 소스, 설계서, SQL 정의를 분석한 계획이다. 업무 코드/DB/외부 설정/배포는 변경하지 않았다. 이번 단계에서 원격 DB의 현재 메타데이터나 계정 목록을 조회하지 않았으므로 운영 스키마와의 실제 일치 여부 및 데이터 중복 분포는 구현 전 읽기 전용 사전 점검 항목이다.

## 현재 구조

근거: server/postgres-schema.sql, server/schema.ts, server/master-data.ts, server/ledger.ts, server/reports.ts, server/backups.ts, src/master-data.tsx 및 docs/accounting_web_codex_spec.md 5.4절.

| SQL 테이블 | 용도 |
| --- | --- |
| cashbook.control | 단일 행의 제어 JSON: 사용자, 부서, 배정, 부서별 accounts, 감사이력, 현재 거래 참조, 기초잔액, 마감 등 |
| cashbook.transactions | 부서/거래 ID/버전/해시별 불변 거래 JSON |

| cashbook.sessions | 로그인 세션 JSON |
| cashbook.backups | 복원 전 보관 사본 |

현재 별도 accounts/공통 계정 SQL 테이블이나 코드 발급 시퀀스는 없다. 관계와 유일성은 애플리케이션 JSON 검증에서 검사한다. 부서별 계정은 id(UUID), departmentId, code, name, type(INCOME/EXPENSE), sortOrder, status(ACTIVE/INACTIVE)다.

관리자와 현재 배정 담당자가 자기 부서의 계정을 등록/수정한다. 코드는 직접 입력하며 NFKC 정규화 + 대문자화한다. UUID는 서버에서 발급한다. 동일 부서의 코드 중복을 금지하고 계정 유형 변경도 막는다. 삭제 API 대신 사용 중지를 제공한다.

거래는 departmentId와 부서 계정의 accountId를 참조한다. 거래 저장/조회/복원에서 부서와 수입·지출 유형을 검사한다. 통계와 Excel은 해당 부서 계정 ID로 집계한다. 비활성 계정의 과거 거래도 유지한다. 현재 과거 거래 표시명은 부서 계정의 현재 이름을 사용하므로 이번 변경에서 기존 계정명을 자동 수정하지 않는다.

동시 저장은 동일 PostgreSQL 클라이언트의 control 행 FOR UPDATE, revision 확인, 스키마/체크섬 검사, 스냅샷과 control 갱신을 묶은 기존 트랜잭션을 재사용한다. 순수 JSON 저장소 자체에 원자성이나 분산 카운터가 있다고 가정하지 않는다. control 한 행을 공유하므로 서로 다른 부서도 저장 시 잠금 경합이 생길 수 있다는 기존 한계가 있다.

## 권장 모델: 공통 원본 + 부서별 독립 복사

공통 과목을 직접 거래에 연결하지 않는다. 공통 마스터에서 선택한 항목을 부서별 accounts에 복사하고 새 부서 계정 UUID를 발급한다. 거래는 계속 기존처럼 부서 계정 UUID에 귀속된다.

공통 원본 → 부서 계정 복사본 → 해당 부서 거래

다른 부서는 같은 원본을 가져와도 서로 다른 accountId/상태/사용 이력을 가진다. 담당자 교체 시에도 이 연결은 부서에 유지된다. 공통 원본을 수정하거나 중지해도 기존 부서 계정이나 과거 거래를 일괄 수정하지 않는다.

### 공통 마스터 standardAccounts (control의 선택적 배열)

- id: UUID, 영구 식별자
- code: 관리자용 표준 코드, 정규화 후 전체 마스터에서 유일
- type: INCOME 또는 EXPENSE
- majorCategory, minorCategory: 대분류/소분류
- name: 과목명
- status: ACTIVE 또는 INACTIVE
- sortOrder, version, createdAt/By, updatedAt/By

동일 유형/분류/정규화 이름의 중복을 검사한다. 유형은 생성 후 변경하지 않고 다른 유형으로 새 과목을 만든다. 분류는 관리자 입력/기존 분류 선택으로 관리하며 별도 SQL 분류 테이블은 이번 단계에 추가하지 않는다.

초기 ‘교회 전체 표준 목록’의 내용은 교회의 실제 회계 기준을 확인해 승인해야 한다. 프로그램이 임의의 샘플을 공식 표준으로 등록하지 않는다. 목록 초안에는 예를 들어 수입/회비/정기회비/회원회비, 수입/지원금/교회지원/교회지원금, 지출/선교활동/선교지원/선교비 등을 검토용으로 제시할 수 있으나 확정 데이터가 아니다. 기존 부서 과목은 읽기 전용 후보 추출 자료로만 사용한다.

### 부서 accounts의 추가 선택적 필드

- standardAccountId: 가져온 원본 UUID
- standardAccountVersion: 가져올 당시 원본 버전
- majorCategory, minorCategory: 가져올 당시 분류 복사본
- importedAt/By: 도입 이력

기존 id/code/name/type/status는 유지한다. 신규 선택 필드가 없는 기존 계정도 유효하다. 원본 ID는 출처 메타데이터이며 회계 계산의 외래키가 아니다. 다른 환경의 부서 백업을 복원해 현재 마스터에 원본 UUID가 없어도 부서 계정/거래는 유지하며 ‘원본 확인 필요’로 표시한다. 활성 원본 존재/유형/상태는 신규 가져오기 시 반드시 확인한다.

## 코드 발급·중복·수정 정책

- 가져오기에서는 담당자가 코드를 입력하지 않는다. 서버가 해당 부서의 사용 중/중지 코드 전체를 검사해 수입 I000001, 지출 E000001 형식의 다음 빈 코드를 발급한다. 기존 코드와 충돌하면 건너뛴다. 영구 소진 시 오류로 중단하며 번호를 재사용하지 않는다.
- 코드 발급, 중복 확인, 부서 계정 생성, 감사이력을 같은 검증된 저장 트랜잭션에서 수행한다. 브라우저의 max+1이나 독립 API 사이의 카운터를 사용하지 않는다.
- (departmentId, standardAccountId)는 등록 상태와 관계없이 한 번만 허용한다. 이미 활성인 것은 ‘사용 중’, 중지된 것은 ‘등록됨·사용 중지’로 표시하고 체크를 막는다. 중지 계정은 기존 ID로 재활성화할 수 있다.
- 기존 수동 계정과 이름/유형이 유사하면 ‘기존 과목 확인 필요’를 표시하고 자동 연결/병합/재코드화를 하지 않는다. 이름만으로 동일 과목이라 확정하지 않는다. 관리자가 미리보기 후 명시적으로 원본 연결을 승인하는 별도 절차를 제공하며 id/code와 거래 참조는 보존한다.
- 기존 수동 등록/수정 경로는 호환성 유지를 위해 ‘직접 등록’ 보조 기능으로 보존하는 것을 권장한다. 새 기본 진입은 ‘공통 계정과목에서 가져오기’다. 가져온 계정의 원본/유형은 일반 수정 폼에서 바꾸지 않는다.
- 공통 중지는 신규 가져오기만 막는다. 부서 계정은 별도 중지하며, 부서 중지 계정은 신규 거래 선택에서 제외하고 과거 조회/집계/Excel에서 유지한다. 공통 변경을 부서 복사본에 자동 전파하지 않는다.

## API와 화면

| API 제안 | 권한/동작 |
| --- | --- |
| GET /api/standard-accounts | 인증 사용자 공통 목록 조회. 특정 부서의 등록 상태를 포함하면 해당 부서 권한부터 검사 |
| POST/PATCH /api/admin/standard-accounts | 관리자만 생성/수정/중지. revision/변경 사유 검사 및 감사 기록 |
| POST /api/accounts/import | 관리자 또는 현재 배정 담당자. departmentId, standardAccountIds, expectedRevision, requestId, reason 입력. 대상 부서/활성 상태 재검사 |
| 기존 /api/accounts | 부서별 목록/기존 계정 수정·중지·직접 등록 유지 |

가져오기는 최대 100개씩, 원본 중지/원본 변경/중복/권한을 트랜잭션 안에서 다시 확인한다. 동시에 등록되었거나 조건이 바뀌면 전체 요청을 충돌로 거부하고 새로고침을 안내한다. 일부만 조용히 저장하지 않는다. 응답 유실 후에는 같은 requestId의 처리 기록과 현재 원본 연결을 조회해 결과를 확인한다. 실패인지 불명확한 경우 자동으로 다시 저장하지 않는다.

담당자 계정코드 화면에는 현재 부서의 등록 과목과 ‘공통 과목 가져오기’를 배치한다. PC는 넓은 모달, 모바일은 전체 화면 선택 패널로 구성한다. 이름/분류 검색, 수입·지출 및 대/소분류 필터, 체크박스, 현재 검색 결과 중 선택 가능 항목 전체 선택, 선택 수/등록 결과를 표시한다. 페이지나 필터를 바꿔도 선택 수를 명시하고 가져오기 직전 선택 목록을 확인한다. 이미 등록된 항목은 상태를 표시하고 선택하지 못한다.

관리자는 별도 ‘공통 계정과목 관리’에서 원본을 관리한다. 일반 담당자에게 관리 버튼을 숨기는 것과 별개로 API에서 관리자 여부를 검사한다. 공통 목록에는 다른 부서의 거래/잔액/사용 부서 목록을 노출하지 않는다.

신규 과목 요청 기능은 2단계로 권장한다. 요청자/부서/희망 유형·분류·이름·사유/검토 상태를 JSON에 저장하고 관리자가 승인·거절한다. 승인해도 부서에 자동 등록하지 않으며 공통 마스터 생성 후 담당자가 가져온다. 외부 이메일 발송이나 Auth0 권한 추가는 필요하지 않다.

## DB 변경·이전·복원 계획

1. 승인 후 테스트 DB의 실제 테이블/제약과 기존 계정·거래 참조·중복을 읽기 전용 확인한다. 원본 백업과 체크섬을 검증한다. 운영에는 실행하지 않는다.
2. 새 SQL 테이블/열/인덱스/권한 변경 없이 control JSON 모델만 확장한다. 기존 저장 구조를 유지한다. 신규 기능용 스키마 검증과 감사 동작을 추가한다.
3. 새 컬렉션/필드는 optional로 읽고, 기존 레코드를 parse할 때 빈 배열/기본값을 강제로 추가하지 않는다. 현재 저장소는 검증 후 직렬화한 값으로 체크섬을 비교하므로 무심코 default([])를 추가하거나 기존 필드 순서를 바꾸면 과거 control/스냅샷 체크섬을 깨뜨릴 수 있다. 기존 JSON의 파싱/직렬화 체크섬 호환 테스트를 선행한다.
4. 승인된 표준 목록을 검증·중복 미리보기 후 한 번의 관리자 트랜잭션으로 등록한다. 기존 부서 계정에는 출처를 자동 추가하지 않는다. 기존 거래/불변 JSON/해시/잔액/마감은 재작성하지 않는다.
5. 원하면 기존 계정과 표준 원본의 연결 후보를 미리보기하고, 별도 관리자 승인으로 선택적 출처 연결만 수행한다. 필수 자동 마이그레이션은 없다.
6. 백업 포맷을 명시적으로 버전 관리한다. 기존 v1 백업을 계속 읽고 신규 부서 계정의 추가 메타데이터를 보존한다. 부서 회계 복원은 공통 원본/권한을 변경하지 않는다. 원본을 덮어쓰지 않고 없는 출처는 미확인 메타데이터로 유지한다. 공통 마스터 전체는 관리자 전용 별도 백업/검증·복원 범위를 제공하고 전체 control 스냅샷에도 포함한다. 구버전 실행 파일이 새 필드를 거부하므로 단순 코드 롤백 대신 백업과 새로 발생한 거래를 대조하는 통제된 복구가 필요하다.

단일 control 행의 저장 경합과 JSON 크기는 계속 관리해야 한다. 규모가 커져 별도 SQL 테이블이 필요하면 그때 성능 근거와 권한/복원 설계를 별도 제안한다.

## 승인 후 구현 순서와 테스트

1. 호환 스키마/공통 원본 관리자 API/초기 목록 승인·등록 도구.
2. 트랜잭션 기반 다중 가져오기·자동 코드·중복/동시 요청/API 권한 테스트.
3. 세 테마 공통 선택 화면·모바일·기존 직접 등록 호환·요청 기능(선택).
4. 백업 v1/v2·원본 미존재 부서 복원·감사 및 통계 회귀 검수.
5. 테스트 사이트 실제 담당자 검수 후 운영 적용 별도 결정.

필수 테스트: 일반 담당자의 원본 쓰기 403, 다른 부서 조회/가져오기 403, 중복 클릭·동시 가져오기·코드 충돌, 원본 중지 경쟁, 한 항목 오류 시 전체 미반영, 응답 유실 후 결과 확인, 기존 계정 ID/코드와 거래 JSON/합계·마감 보존, inactive 과거 통계 유지, 옛 스냅샷 체크섬, 옛 백업 복원, 다른 환경 마스터 UUID 미존재 복원, 모바일 키보드/스크롤/다중 선택 및 이전 계정 캐시 정리 회귀.

## 승인받을 권장 범위

공통 원본과 부서별 독립 복사, SQL DDL 변경 없음, 신규 가져오기 코드 서버 자동 발급, 기존 직접 등록 보조 기능 유지, 공통 수정/중지의 자동 전파 없음, 초기 표준 목록 내용은 별도 확인 후 등록하는 방향이다. 과목 추가 요청은 기본 가져오기 안정화 후 2단계로 둔다. 승인 전에는 구현하거나 기존 데이터를 이전하지 않는다.
