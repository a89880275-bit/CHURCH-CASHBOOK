# 주내교회 부서 회계관리

최신 구현: **통계·대시보드** — 월별 차트, 계정별 월별 집계, 연간 결산 조회, 관리자 부서 비교, 상세 장부 이동. [3단계 구현·검증 보고서](docs/stage3-reports.md)

최근 추가: 대시보드·장부 맨 앞 **이월금액** 카드 및 **부서별 월별/연도별 조회 방식**. 관리자는 부서·담당자 관리 → 수정 → 회계 관리 방식에서 설정합니다. [변경 및 검증 보고](docs/carry-period-update.md)

단일 요구사항 기준: [accounting_web_codex_spec.md](docs/accounting_web_codex_spec.md). 원문을 유지합니다.

현재는 **기초정보와 수입·지출 장부가 로컬 비공개 JSON에 실제 저장**됩니다. 사용자·부서·담당자·계정코드 관리에 이어 거래 등록·수정·논리삭제·검색·합계·기초잔액·이력과 통계·대시보드를 구현했습니다. 마감 실행·Excel·웹 백업/복원은 다음 단계이며 Netlify 운영 연동은 아직 미검증입니다.

최신 실행·테스트·변경 파일은 **[2단계 장부 보고서](docs/stage2-ledger.md)**, 기초정보 구현은 [1단계 보고서](docs/stage1-review.md)를 확인하세요. 이전 보고서는 당시 상태의 기록입니다.

## 실행

Node.js 24, pnpm:

```powershell
pnpm install --frozen-lockfile
# 터미널 1
pnpm server
# 터미널 2
pnpm dev
```

[로컬 화면](http://127.0.0.1:5173/users)에 접속해 `초기 관리자 · 관리자`를 선택합니다. 처음 실행 시 관리자 1명만 생성하며, 예제 부서·담당자·계정은 생성하지 않습니다. 사용자가 등록한 정보는 `.private/accounting/current.json`에 저장되고 재시작해도 유지됩니다. 이 폴더는 Git 및 정적 배포 대상에서 제외하며 Vite 직접 다운로드도 차단합니다.

이 로그인은 **비밀번호 없는 루프백 검수용**입니다. 공개 서버나 실제 운영 인증으로 사용할 수 없습니다. API는 `127.0.0.1:8889`, UI는 `127.0.0.1:5173`에만 바인딩합니다. Origin 검사가 있으므로 `localhost` 대신 위 주소를 사용하세요. 이미 실행 중인 구버전 API는 종료 후 `pnpm server`로 다시 실행해야 합니다.

사용 순서:

1. 사용자 관리 → 담당자 등록.
2. 부서·담당자 관리 → 부서 등록 → 담당자 배정 → 사유/미리보기 → 적용.
3. 상단에서 특정 부서 선택 → 계정코드 관리 → 수입/지출 계정 등록.
4. 변경 사유와 before/after는 감사이력에서 확인.
5. 수입·지출 장부 → 부서 선택 → 수입/지출 등록, 기간·계정·적요로 검색.
6. 관리자가 검증한 기초잔액과 적용일을 설정하면 기간말 누적잔액을 확인할 수 있습니다. 미설정은 0원이 아닌 미설정으로 표시합니다.
7. 각 거래의 수정·삭제·이력 버튼을 사용할 수 있습니다. 수정/삭제 사유는 필수이고 최초 작성자는 보존합니다.
8. 로그아웃 후 담당자로 로그인하여 배정된 부서만 접근하는지 확인.
9. 대시보드에서 조회 기간과 월별 추이를 확인합니다. 통계·보고서에서 월별·계정별·연간 자료를 조회하고, 월이나 계정 금액을 클릭하면 해당 조건의 장부로 이동합니다. 전체 부서 통계와 부서 비교는 관리자 전용입니다.

수정 시 사용 중지 상태를 선택해 중지할 수 있습니다. 물리 삭제 기능은 제공하지 않으며, 마지막 활성 관리자의 중지/권한 해제는 서버에서 차단합니다. 모든 담당자 선택을 해제하면 해당 부서의 배정을 모두 해제합니다. 현재 배정 변경은 한국 날짜 기준 오늘 즉시 적용만 지원합니다.

## 검증

```powershell
pnpm test
pnpm build
node scripts/check-dist.mjs
```

실행 환경에 npm이 없으면 위 두 서버를 별도 터미널에서 실행하세요. `dev:full`의 npm 별칭은 npm이 설치된 환경을 전제로 합니다. 테스트는 임시 디렉터리의 가상 자료를 사용하고 사용자용 JSON에 검증 데이터를 넣지 않습니다.

저장소는 독점 디렉터리 잠금·revision 충돌 검사를 사용합니다. 충돌은 `409`이며 재조회 후 다시 저장해야 합니다. 변경 전 사본 생성·후보 파일 flush·동일 디렉터리 rename으로 공개 파일을 교체합니다. 스키마/체크섬 오류와 저장 실패는 성공으로 처리하지 않습니다. 검증한 로컬 디스크 범위의 결과이며 전원 차단·공유 드라이브·Netlify 분산 저장의 원자성을 보장하지 않습니다.

거래는 `transactions/부서ID/거래ID/버전-해시.json`에 보관하며, 제어 JSON의 유효 참조만 조회합니다. 독립 거래는 모두 저장하고 같은 거래의 동시 수정은 409로 차단합니다. `snapshots`는 동일 디스크의 변경 전 복구 사본이며, 거래 복구에는 해당 사본이 참조하는 거래 객체도 함께 필요합니다. 원격/자동 백업이나 웹 복원 기능이 아닙니다. 비정상 종료 후 `write.lock`이 남으면 강제로 자동 회수하지 않고 저장을 차단합니다. 서버를 모두 중지하고 원본/복구 사본을 보존·검증한 뒤 관리자 점검이 필요합니다. 직접 JSON 파일을 편집하면 체크섬 검증에 실패하며 초기값으로 덮어쓰지 않습니다.

## Netlify 운영 연결

기존 Functions·Blobs 어댑터·OIDC 코드를 유지합니다. **FileRepository는 Netlify Functions에서 사용하지 않습니다.** Netlify의 임시 파일시스템을 영구 저장소로 취급하지 않으며 원격 Blobs 업무 쓰기도 계속 차단합니다.

1. 관리형 OIDC 제공자(우선 후보 Auth0)에 confidential web app과 계정을 발급합니다. redirect URI는 `https://사이트주소/api/auth/callback`입니다.
2. `.env.example` 설정을 Netlify Functions 전용 환경변수로 지정합니다. 비밀값에 `VITE_*`를 사용하지 않습니다. APP_ORIGIN은 끝 슬래시 없는 HTTPS origin, COOKIE_KEY는 안전하게 생성한 32바이트의 64자리 hex입니다.
3. 제공자의 검증된 `sub`와 실제 관리자를 비공개 제어 JSON에 매핑해야 합니다. 로컬 `local:*` 계정은 운영용이 아닙니다. 계정 자동 프로비저닝/비밀번호 초기화는 제공자 API를 임의로 구현하지 않았습니다.
4. 원격 JSON 저장소를 격리된 환경에서 읽기·쓰기·경합·장애·배포 지속성 검증하고 운영 쓰기를 구현해야 합니다. 실제 업체 계정 생성·비용 지출·Netlify 배포는 아직 수행하지 않았습니다.
5. 사이트 범위 Blobs 공유 위험 때문에 미리보기/브랜치 배포의 운영 자료 접근은 차단합니다.

운영 제약과 저장 대안은 [구현 계획](docs/implementation-plan.md), 최신 상태와 파일별 결과는 [2단계 보고서](docs/stage2-ledger.md)를 참조하세요.
